# Adding parts to Circuitoon

Circuitoon sheets are used to physically wire real circuits. A part with a wrong pin order causes a miswire on a real board, which is worse than the part not existing. Everything below serves two goals: the pins are exactly right, and the part reads instantly on a sheet.

Read `docs/PRD.md` ("Module definition format", "Art studio", "Built-in parts") before your first part in a session; it is the spec. `references/conventions.md` has the look, palette, geometry and category rules this skill relies on.

## Workflow

1. **Pin down what the part is.** For a product link, fetch the page and identify the exact module (maker, model, controller chip, variant). Amazon usually works with WebFetch; AliExpress redirects to a login page, so ask for the product title or check Michael's notes (`C:/Users/micha/Desktop/Claude/Projects/`) for an order. If variants exist (for example 4-pin OLEDs sold as GND-VCC-SCL-SDA and VCC-GND-SCL-SDA), decide which to ship; widespread variants each get their own module with the order in the name.

2. **Source the pinout.** Never put Michael's email address or any other personal data in a web request (search queries, URLs, form fields, headers); searching and fetching need nothing about him. Fetch the manufacturer's documentation: datasheets (Microchip, Espressif, Raspberry Pi), maker wikis (Seeed wiki, lcdwiki.com, Adafruit, Waveshare, SparkFun). For generic clones with no maker page, use the best vendor image plus one independent source that agrees. Record every URL in the module's `source` field (space-separated). Official pinout PDFs often have no text layer: render the page to an image (Python with PyMuPDF: `pip install pymupdf`, then `fitz.open(pdf)[0].get_pixmap(dpi=200).save(png)`) and read it. Official Fritzing parts (`.fzpz`, listed on maker pages) carry a machine-readable connector list and make a good cross-check. If you cannot verify a pin, leave the part out and say so. Never fill gaps from memory.
   **Mains parts** (anything that touches the wall: outlets, plugs, chargers, AC-DC modules, lamp and fuse holders, SSRs, relay contacts, terminal blocks) are researched into `src/format/mainsEvidence.ts` first: the exact part or standard, every URL, each value with the source line it came from, and a verdict. That file is the source of truth; it is reviewed before any part is generated, generators import from it and tests compare the parts against it. Isolation is never inferred: record only a class the source states for the mains-to-output barrier (reinforced, double, basic). A test voltage, a class II symbol alone, an SELV or ES1 label or a safety listing is not a class; the part then gets `isolation: "unknown"`. The one exception: a manufacturer's explicit written "Class II" is recorded as `double` (IEC 61140), with the quote. See "Mains parts" in `references/conventions.md`.

3. **Choose id, name and category.**
   - `id`: lowercase kebab-case, descriptive and stable (`tft-ili9341-28-spi-touch`). Designator prefixes key off the id (see `src/editor/ops.ts` PREFIXES; first match wins, in this order): the mains families first, each anchored to its own id prefix: `outlet-` XS, `plug-` XP, `charger-|adapter-|hlk-|irm-` PS, `lamp-holder-` E, `fuse-holder-` F, `ssr-` K, `terminal-block-|wago-` X; then `potentiometer*` gives RV, `resistor*` R, `capacitor*` C, `led*` D, `ws2812*` D, `*button*|*switch*` S, `battery*` BT, `lcd-|oled-|tft-` DS, `piezo*|buzzer*` BZ, `relay*` K, `servo*` M, `jst-|dupont-|usb-panel-` J, everything else U. Add a prefix rule (with a test) if a new family needs one; anchor it (`^family-`) and check it takes no existing id (the PREFIXES test in `src/editor/ops.test.ts` lists neighbours a careless rule could catch).
   - `name`: what a maker would call it, with the distinguishing detail ("ESP32 DevKit V1 (30 pin, DOIT)").
   - `category`: an existing group from `CATEGORY_ORDER` in `src/editor/libraryGroups.ts`. Michael asked that the Parts panel stay organized as it grows: if a new family does not fit, add a category there deliberately (in a sensible position, with the test updated) instead of dumping it into a loosely related one. Every part that touches mains (outlets, plug-in devices, cord plugs, AC-DC modules, lamp and fuse holders, SSRs, mains terminal blocks and Wago connectors) goes in `Mains`, the last named category; a low-voltage part that can also switch mains (a relay module, the KCD1 rocker) keeps its own category and just declares its mains data. Look at how full each group is; when one gets crowded, propose a split.

4. **Encode the pins.** See "Pin rules" below. Physical order is the whole point: lay pins out as seen from the component side in the vendor's diagram orientation.

5. **Draw the art** in the Sticker style (rectangles only; the renderer adds the ink outline). See `references/conventions.md`. For families of similar parts, extend or add a generator script in `scripts/` (existing: `gen-boards.mjs` for ESP32, Arduino Nano and D1 mini boards, `gen-arduino.mjs` for the rest of the Arduino family (Uno, R4, Leonardo, Zero, Mega, Due, Micro, the newer Nanos, Pro Mini; its `place` puts each header on its real row), `gen-picos.mjs` for the Raspberry Pi Picos, `gen-parts.mjs` for chips, displays and microSD modules, `gen-power.mjs` for power modules, `gen-sensors.mjs` for addressable LEDs and sensor modules, `gen-outputs.mjs` for relay, servo, motor driver, radio and level shifter modules, `gen-typewriter.mjs` for the Spirit Typewriter parts: tilt and tactile switches, the ESP32 screw terminal adapter, the panel pot, USB panel-mount cables, JST-XH headers and Dupont housings, `gen-breadboards.mjs` for breadboards and rail strips, `gen-mains-outlets.mjs` for wall outlets, `gen-mains-plugs.mjs` for USB chargers, barrel adapters and cord plugs, `gen-mains-loads.mjs` for AC-DC modules (Hi-Link, Mean Well IRM), lamp holders, the fuse holder and Wago connectors, `gen-mains-terminals.mjs` for terminal blocks, `gen-usb.mjs` for the Raspberry Pi 4, 5 and Zero 2 W (the 40-pin header as pads in physical order), the computer USB port and the USB hubs; `gen-outputs.mjs` also holds the Fotek SSR and the relay module's contact data; mains generators build sockets, plug profiles, prong nodes and ratings with `scripts/lib/mains.mjs` and read every value from `src/format/mainsEvidence.ts`) so pin lists live in one readable table; the generator must reproduce the committed JSON byte for byte. Name it `scripts/gen-<family>.mjs` and write its files through `emit`/`log`/`finish` from `scripts/lib/gen-output.mjs` so it supports `--check` (part generators get that for free through `write` in `scripts/lib/parts.mjs`, which also holds the shared `r`, `slots`, `side` and `moduleJson`, which takes `holes` and `obstacle` for board-like parts such as outlets; use them rather than copying); `npm run check:gen` (scripts/check-gen.mjs) picks up every `gen-*.mjs` automatically and fails one that does not import that helper.

6. **Map it to KiCad.** Give the part its `kicad` footprint and pad numbers, or put it in `UNMAPPED` in `scripts/lib/kicad.mjs` with the reason. See "KiCad mapping" in `references/conventions.md`: footprints from KiCad's standard library only, pads read from the footprint file and listed in `src/format/kicadFootprints.testing.ts`.

7. **Update the lists that name parts.** Every built-in part needs its entry in `src/format/partText.json`: a one-sentence `description` and 1 to 8 `uses`, which the closest-match search (`src/format/partSearch.ts`, the Parts panel and `circuitoon parts --search`) ranks on and the panel shows as the tooltip. See "Part text" in `references/conventions.md`; never put them in the module JSON. If the part uses `pinLabels: "inside"`, add it to the allowed list in `src/format/module.test.ts`; add it to the Built-in parts table in `docs/PRD.md` (move it out of the "Not built yet" line if it was there).

8. **Validate and test.** `npm run validate` (every module), `npm run check:gen` (for a generator family: every generator rebuilds its files in memory and fails if one differs from modules/, so a hand edit to a generated file or a generator change without re-running it is caught; the deploy runs it too), `npm test` (includes the two-lead geometry test and board/part tests; add a test pinning the pin order for multi-pin parts, like `src/format/boards.test.ts` and `parts.test.ts` do), `npm run build`, then `npm run build:cli`: the agent toolkit's CLI bundle embeds every module, so commit the regenerated `plugin/dist-cli/circuitoon.mjs` with the part (`npm run check:gen` fails otherwise). Run `build:cli` before `check:gen` when both are needed.

9. **Look at it.** `npm run build`, then
   `node .claude/skills/circuitoon-add-part/scripts/shoot-parts.mjs <id> [more ids] --out <scratchpad dir> [--panel] [--rotate 90] [--dark] [--fill 0.8]`
   (`--fill 0.8` for tall boards so labels come out large; `--panel` filters the Parts panel to the part's group)
   and Read every image. Check: leads meet the metal pin stubs, labels readable, nothing overlaps, it looks like the real thing, the Parts panel group reads well. Redraw anything that reads poorly and shoot again. Never use the Playwright MCP browser (shared with other agents).

10. **Independent pinout check before merge.** Have a reviewer who did not write the part fetch the sources and compare every pin row, in order, against them (for subagent workflows, dispatch this as the task review with WebFetch access). Record the verdict per part: MATCHES, MISMATCH with differences, or NOT VERIFIED. For mains parts the review covers every pin, contact, plug profile, rating (value, service, provenance, conditions) and the isolation class against `src/format/mainsEvidence.ts` and its sources; a MISMATCH or NOT VERIFIED blocks the next batch, and nothing NOT VERIFIED is generated as if verified.

11. **Ship** with the `circuitoon-ship` skill (merge, deploy, live check, vault note).

## Pin rules

- Pins sit on the body edges at 10 px pitch (0.1 inch), placed in array order: left to right on top/bottom, top to bottom on left/right, centered on the side at whole grid units. `{ "spacer": true, "side": ... }` holds an empty slot so pins line up with a physical gap.
- `name` must be unique; use the silkscreen text. Duplicates (several GND pins) become "GND", "GND 2", "GND 3" in physical order with `label: "GND"` so the sheet shows the silkscreen.
- `type`: `power_out` for rails the part supplies (a board's 3V3 regulator output, a battery +), `power_in` for inputs (VCC, VIN, 5V), `ground`, `input` for input-only pins (for example ESP32 GPIO34-39), `output` for output-only, `io` otherwise, `passive` for two-lead parts, `nc` for no-connect.
- `supply`: the voltage the pin actually sees ("3V3", "5V", "9V", "3.7V" for a Li-ion cell), never a symbolic rail name like "VBAT". A power input that accepts several rails lists every one its datasheet range covers with "/" ("3V3/5V"), which keeps a later wrong-voltage check from flagging valid hookups. An adjustable output is "ADJ" (user-set). See "Supply names" in `references/conventions.md`.
- `internal`: join pins that are the same net on the part (all GNDs of a board).
- Values: a part with a user-editable value declares it in `electrical.params` named exactly `resistance`, `capacitance` or `voltage` (with `unit` and `default`); only those names show in captions and the value picker.
- Polarized two-lead parts label their pins "+" and "-".
- Header pins drawn inside the body next to each pin, like silkscreen, are opt-in with `"art": { ..., "pinLabels": "inside" }`. As applied: every part whose pins are a named header, pads or terminals (boards, the ESP32 terminal adapter, display, storage, power, sensor, relay, motor driver, radio and level shifter modules, 3-pin ones such as the AMS1117, DHT22 module, HC-SR501 and the SG90 servo lead included), multi-lead components whose leads carry signal names (WS2812D 5 mm LED, bare DHT22), the USB panel-mount cables, the Raspberry Pis and the USB hub boards. DIP chips are drawn at true scale (a 300 mil DIP's rows 30 px apart, so it seats in rows e and f) and use `"pinLabels": "tips"` instead: names past each pin's tip, since a 30 px body has no room inside. Not on two-lead parts (batteries, passives, LED, buzzer, push, rocker, tilt and 4-pin tactile switches), numbered connector housings (JST-XH, Dupont) or the pots (potentiometer, WH148 panel pot), which keep the default labels.
- Analog grounds (AGND, a separate analog ground plane) stay out of the GND `internal` group unless the maker documents the pin as ground on the board (Raspberry Pi: Pico AGND is "also a GND pin", so it is joined); say which in the report. A part left with separate ground components and supplies needs `electrical.returns`.
- A few pads inside the board (debug pads, test points) with no edge position: until interior pins land, bring them out as pins on the nearest edge in their physical order and draw thin traces from the true pad spot to the edge, and say so in the report. A full 2-row header is different: defer it (next rule).
- Body size for boards with pins on several sides: height from the longest side's slot count plus corner margin; width a multiple of 10 px that fits the art and the other sides' pins; check the bottom or top pins still center where the drawn pads are.
- Two-lead parts: art height must give an even number of grid units so the single left/right pin lands on the drawn lead center (the geometry test enforces this).
- **Pin capabilities (`caps`).** For every MCU, I/O expander or other chip with pins that cannot do everything, mark what the chip maker's datasheet says, and nothing else: `inputOnly` (no output driver: ESP32 GPIO34-39, Nano A6/A7), `outputOnly` (MCP23017 GPA7/GPB7), `flash` (wired to the module's SPI flash or PSRAM: ESP32 GPIO6-11), `noPullup` (no internal pull-up or pull-down), `strapping` (`"high"`, `"low"` or `"either"`: the level the boot needs at reset; "either" when both levels boot and it only changes a detail such as the boot log), `downloadOnly` (with "high" or "low" when that level only matters for entering the serial download mode, as on ESP32 GPIO2: the message then says flashing, not boot) and `note` (allowed on any part, not only chips: one plain sentence a hobbyist understands, informational, such as a GPS RX's 3.6 V limit: "GPIO12 (MTDI) high at reset sets the flash voltage to 1.8 V, and the 3.3 V flash on this module then fails to boot."). The checker's pin rules and `circuitoon explain` read them; a wrong cap is a wrong finding, so treat each one like a pin: cite the datasheet section in the generator next to the table, cross-check it against a second, independent source, and when the two disagree follow the datasheet and say so in a comment. Mark only pins the board actually breaks out, map header names to GPIO numbers from the board maker's pin table, and put the board's header name in the note when it differs ("D9 is GPIO9. ..."). Chip-wide tables live in `scripts/lib/pin-caps.mjs` (ESP32, ESP32-S3, ESP32-C3); reuse them.
- **USB ports.** A USB socket or plug is one pin with `type: "usb"` and a `usb` object (connector, gender, role, and only what a source states of version, speed, `source` or `draw` mA, `power: "only"` for a charge-only input, `hub`, `through`); never separate VBUS/D+/D- pins. Build them with `scripts/lib/usb.mjs`: `usbPort`, `portSide(side, len, [[px, port]])` to put a port where the real connector is on a free side, `intoSpacer` to take a spacer's slot on a side that has pins. On an existing part, append ports (or take spacers) so no other pin moves: stored copies then get Update parts, not a block (`moduleDrift`, Ruling U1). Role: `dual` only when the board's maker documents host or OTG use of that port; a USB-to-UART bridge port is a `device`. An unknown draw stays out: never guess it. Pin `src/format/usbParts.test.ts` with the port and add the part's row to `.superpowers/usb-pinouts.md`. Where the board's schematic or docs say which pin USB VBUS feeds (its `electrical.external` pin), set `vbus` on the port (`withVbus` in `scripts/lib/usb.mjs`): the checker warns on a supply there while a host powers the port. KiCad needs nothing: USB links are off-board, and `scripts/lib/kicad.mjs` leaves `usb` pins out of header mappings.
- **I2C devices (`electrical.i2c`).** `{ "sda", "scl", "address"?, "pullups"? }`: the bus pins, the 7-bit address (`fixed`, `base` plus address `pins` each with its `add` and, only when the board's schematic or two sources say so, the `floating` level the board pulls it to; or `setting` for a resistor or jumper on the board, with matching `electrical.settings` choices such as `["0x3C", "0x3D"]`, the shipped default first), and `pullups` only when two sources agree whether the board has SDA/SCL pull-ups (leave it out otherwise; the checker then asks the user to check). Never mark I2C from pin names alone: SPI displays label their lines SCL and SDA.
- Pins in the interior of a body (a 2x20 header in its true position) are hole groups: `"holes": [{ "name": "GPIO2", "label": "GPIO2", "at": [[x, y]], "holeStyle": "pad" }]`, one single-position group per header pin, each on a 10 px grid point inside the body. A pad takes `type` and `supply` exactly as a pin does (`{ "name": "3V3", "at": [[x, y]], "holeStyle": "pad", "type": "power_out", "supply": "3V3" }`); breadboard strips and rails set neither. Names share the pin namespace. Never fake an interior header by spreading its rows onto opposite edges.

## Things that went wrong before (keep them from recurring)

- Leads drawn 5 px off the pin because the art height was an odd number of grid units.
- A vendor diagram showing the back of the board: mirror it to the component side and confirm with a front photo.
- A label changed after the screenshots were taken and never re-checked: re-shoot after every art change.
- `git stash` is shared between worktrees; never use it. Never switch branches in a worktree another agent uses.
- Captions showing an irrelevant value (an LED's forward voltage): only resistance, capacitance and voltage are captioned.
